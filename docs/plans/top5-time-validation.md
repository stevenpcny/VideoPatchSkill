# 最耗时五项：方案与验证

实测可用方案是：Windows Reader请求1MiB读取管道，并用精确查找表执行固定调色。在本机4K/240帧完整CLI的五对交替复测中，中位数27.68→19.54秒，节省29.4%，每次约8.13秒；实际编码文件逐字节一致。

本研究针对当前视频补丁处理链，不把人工审看、外部生成等待或不同电脑的任务混在一起排名。所有媒体均为确定性合成素材。实验工具是 `tools/top5_experiments.py`；结果是开发期原型验证，不是已经发布的生产默认功能。

## 测量合同

- 基准提交：`28b7c5ab0cfe6eb4f77d6f7a839e39c7f2c403c0`。
- 3840×2160、24fps、完整240帧；一个640×640多频段补丁，三级金字塔，非恒等固定调色；8位SDR。
- 使用已核查的现有Rust内核，Python处理线程4、编码线程4、OpenCV线程4。内核SHA256为`cb790c4cb509bb5fc3c25acdd39035ca0c0149da5dea6b1a40287c3f2585bf82`。
- 固定工作机：Windows、Intel i9-13900K，24核/32逻辑处理器；CPython3.13.16、NumPy2.5.4、opencv-python5.0.0.93、Gyan FFmpeg/ffprobe9.0.2。两侧均已启用Rust，不能将本次收益归为“开启Rust”。
- 基线必须使用实际字段 `gain_bgr` / `offset_bgr`。旧实验配置中的 `color_gain` / `color_offset` 不被当前 `patch_inputs` 消费，不能把该旧实验冒称已调色性能。
- 阶段剖析只统计主线程排他的墙钟时间（包括等待），不把解码器、编码器、工作线程的并行耗时相加。插桩和普通运行的输出文件必须字节相同。
- 每项单独改变一个因素；质量和计时分开；先热身与三对A/A，再运行五对交替AB/BA。只记录暖操作系统缓存，未主动清空系统文件缓存；温度、频率与后台负载未控制。
- 单项候选至少节省10%，且高于A/A噪声才建议组合；最终判断以完整CLI复测为准，不把各阶段节省秒数相加。
- 完整CLI测试包括输入预取、完整输入探测、完整渲染、输出严格解码与音轨载荷核验、文件哈希、报告及发布。A/B都使用相同的4K `--preview`（仅改变编码preset，不改变尺寸或片长），不缩短验证范围。

## 已确认的五项及方案

剖析中两次普通运行26.67/26.79秒；两次插桩26.91/27.09秒，插桩开销约1.02%。下列为两次插桩的阶段中位数；前两项非常接近，不声称其顺序有统计显著性。

| 阶段 | 秒 | 单因素方案 | 正确性条件 |
|---|---:|---|---|
| 解码等待 | 6.291 | 仅限制Reader的FFmpeg解码线程为4、滤镜线程为1 | 源片及返回片全部240帧的原始解码字节相同，不改输入/输出完整核验 |
| 补丁几何与固定调色 | 6.193 | 把每像素float64固定调色改成256×3查找表；保留原resize/warp/fade | 每个uint8值沿用原float64运算顺序、clip及ties-to-even；变换参数是缓存key |
| 多频段融合 | 5.534 | 在此640像素工作区内直接执行现有内核，减少逐层线程池调度 | 不裁金字塔、不改变层数、保护语义和舍入；输出逐位一致 |
| 颜色转换 | 2.361 | 对工作区内转换直接调用现有内核，减少小任务分片调度 | BT.709/BT.601、全/有限范围均逐位一致 |
| 整帧色度整理 | 1.893 | 对现有chroma_avg执行单块处理，检验调度成本与内存带宽的权衡 | 原Y及444→420的ties-to-even规则完全保持，不直接换成原生420解码 |

单阶段实验的解码是独立的完整Reader吞吐，其他阶段采用相同真实函数和固定的代表输入重复240帧。它们说明算子收益，不能将其绝对秒数当作并行流水线中的排他等待时间。阶段收益需要组合CLI复测。

## 质量控制

额外60组控制包含三种尺寸、小数仿射位移、首尾淡变、保护区、不同色彩矩阵与范围。单阶段另比较完整原始帧或返回数组SHA256。组合测试比较实际编码MP4的SHA256、240帧、完整时域、尺寸及原音轨载荷。

相同编码文件字节可以证明候选没有改变基线画面和音轨；本研究不据此宣称基线已通过用户视觉验收，也不声称10bit/HDR、8K、多人物或其他工作区尺寸获得相同收益。

## 复跑

使用既有4K/240帧合成源和640×640/240帧返回片，输出目录必须是新目录：

```powershell
python tools/top5_experiments.py --mode fixture --out NEW_FIXTURE
python tools/top5_experiments.py --mode profile --source SOURCE.mp4 --returned RETURN.mp4 --native-dir PATH_TO_NATIVE --out NEW_PROFILE
python tools/top5_experiments.py --mode experiments --source SOURCE.mp4 --returned RETURN.mp4 --native-dir PATH_TO_NATIVE --out NEW_STAGES --pairs 5
python tools/top5_experiments.py --mode combined --source SOURCE.mp4 --returned RETURN.mp4 --native-dir PATH_TO_NATIVE --out NEW_COMBINED --pairs 5 --selected VALIDATED_STAGE_NAMES
python tools/top5_experiments.py --mode combined --source SOURCE.mp4 --returned RETURN.mp4 --native-dir PATH_TO_NATIVE --out NEW_PIPE_COMBINED --pairs 5 --selected patch_transform pipe_capacity
python tools/top5_experiments.py --mode quality --native-dir PATH_TO_NATIVE --out NEW_QUALITY --selected patch_transform pipe_capacity
```

`PATH_TO_NATIVE`中必须已有当前源码对应并通过自检的内核。工具不安装或下载软件。实验只在本Python进程或实验子进程作用域替换函数，退出后恢复，不修改全局系统环境或安装技能。

## 五项独立实验结果

下表为每项五对AB/BA的中位数。此处解码数值是独立完整Reader吞吐时间，不是上表流水线内的等待时间；不能直接对比或相加。

| 项目 | 原方案秒 | 候选秒 | 结果 | 决策 |
|---|---:|---:|---|---|
| 解码线程限制 | 14.273 | 13.708 | 节省3.96% | 未达到10%门槛，不采用 |
| 固定调色查找表 | 6.295 | 1.080 | 节省82.85% | 进入完整CLI复验 |
| 融合单块执行 | 5.610 | 5.722 | 慢1.98% | 保留现有并行实现 |
| 颜色转换单块执行 | 2.058 | 5.707 | 慢177.25% | 保留现有并行实现 |
| 色度整理单块执行 | 1.974 | 3.789 | 慢91.97% | 保留现有并行实现 |

所有五项的独立质量对照SHA256一致；解码覆盖源片及返回片全部240帧，其余为代表数组，另有60组数值控制通过。查找表在每次B计时前清空，包含构建成本，不把预建表的理想上界冒充实用收益。

这组结果说明本机Rust路径仍依赖有效的多核并行；不能笼统减少线程。固定调色只接收uint8像素与固定每通道参数，256×3查找表可替代重复的大数组float64运算，同时保留原来的数值规则。表本身仅768字节，本实验每个任务一个固定调色表；实际产品若接入长期缓存，仍需有界生命周期和参数失效设计。

## 完整CLI复测及解码等待的后续方案

只使用调色查找表，完整CLI五对中位数27.889→26.851秒，仅节省3.72%。单次重新剖析显示解码等待增加，证明不能把阶段82.85%的收益直接推广到整条流水线。

因此对第一项“解码等待”补测第二个方案：保持原FFmpeg参数、像素格式及线程数，仅通过Windows标准API `CreatePipe` 为Reader请求1MiB匿名读取管道。子进程继续通过Popen复制其stdout句柄，父进程关闭未使用端，退出时沿用Reader关闭与线程回收；不改编码器输入管道。缓存只是一份768字节调色表，管道请求增加量为每个活跃Reader至多约1MiB，不把内核缓冲区预算冒充进程树实测峰值。

先做一对探索：27.976→19.562秒，节省30.07%，输出hash一致。随后重新执行独立的五对完整CLI AB/BA，以下结果不混入那一对探索数据：

| 对次 | 执行顺序 | 原方案秒 | 查找表+Reader管道秒 |
|---|---|---:|---:|
| 1 | A→B | 27.765 | 19.543 |
| 2 | B→A | 28.299 | 19.613 |
| 3 | A→B | 27.534 | 19.735 |
| 4 | B→A | 27.337 | 19.524 |
| 5 | A→B | 27.677 | 19.536 |
| 中位数 | | **27.677** | **19.543** |
| MAD | | 0.143 | 0.019 |

**完整流程节省29.39%，每次8.135秒。** 各次均输出3840×2160、24fps、240帧；原音轨载荷一致；十份MP4的SHA256均为`0023bfbc0ed77ecadf811609cabf98cfdcb0108fb10956545de3859771b48269`。

组合候选另一次诊断中Reader等待0.701秒，补丁变换0.949秒；其他阶段因并行重叠和争用也发生变化，因此总收益仍只采用上述完整CLI墙钟，不加总阶段差值。

## 完成核对与采用建议

- 五项最大开销均有明确方案、五对原始测量、A/A控制及质量对照。[机器可读证据](evidence/top5-time-validation.json)保留全部对次、MAD、版本、基线提交和原型源码SHA256。
- 另有三组完整编码/严格核验对照：动态遮罩+保护区+淡变+小数仿射+None/重复帧映射；多频段淡变；缩放工作区。各组A/B视频文件与原音轨hash一致。
- Windows子进程启动失败注入未吞掉错误，句柄数不变；三组正常任务后句柄数均为364，没有逐任务增长。
- 从工具重新生成4K源和返回片，两份文件均与实际基准输入逐字节一致，证明复跑入口可用。
- 没有改动生产脚本或发行包。六套完整发行回归未重跑；本次验证覆盖实验原型及上述样例，不据此声称已完成发布验收。
- 研究期一次颜色矩阵控制使用了元数据别名而非内部键，另一次fixture命令在创建源片前执行了存在性检查；均在相应计时开始前失败并修正。失败不计入稳态A/B速度，但记录在证据中，不作为成功样本。

建议优先移植并审查**Windows Reader管道容量**与**固定调色查找表**，保留现有融合、颜色转换、色度整理的多核分片。移植时保留句柄失败清理、固定参数缓存生命周期和非Windows原路径，再进行完整发行回归；本报告不把实验脚本的进程内替换当成生产API。

收益限于本机、8位SDR、该工作尺寸与暖OS缓存的合成工作负载。没有测量冷OS缓存、系统物理I/O、进程树峰值RSS、8K、多人物长片或10bit/HDR；不存在这些场景的节时承诺。原始本地视频/日志与含路径的运行报告保留在任务输出目录，不纳入仓库证据。
