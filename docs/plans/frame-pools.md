# 第三轮：完整流程优先，明确缓冲所有权

采用方案是merge内部的有界原始帧池和编码输入池。固定P1基线 `b585a1e` 的五对完整CLI实验，中位数 **17.8005→14.6561秒，节省17.665%**。十份实际MP4及原音轨保持一致。正式实现另一次完整运行14.6408秒、输出hash一致；这条生产确认不替代五对性能结果。

原生向量实验对两个矩阵、全/有限范围穷举全部24位RGB/YUV值：各67108864像素对照一致；另测3063组整数色度和及12组尾部/行步长组合。BGR→UV使用相邻网格分组，不冒称穷举所有四像素排列。严格质量通过仍不能代替完整流程速度证据。

自动向量化还额外构建了同编译器/优化级别的control库，观察到约3%的构建差异；完整流程A侧始终使用原P1库。新向量核及CPU分派都留在开发实验，生产native源码和库ABI没有改动，也无需为本次缓冲复用重建Rust库。

## 正式实现的所有权

- 默认Reader仍逐帧新建raw存储。仅merge显式传入`recycle=True`；prepare不启用，RGB raw不启用。`get()`返回的BGR仍独立，不会被后续raw复用改写。
- 原始帧由解码线程取得，经过队列交给消费方；只有advance离开旧帧后才归还。重复索引保持当前帧，跨帧跳读逐个归还中间帧，短帧不发布。停止事件可中断池等待。
- 编码输入由生产方取得，write提交后保持在途；只有写线程的write调用结束才归还。失败写入也归还，错误继续传播。重复提交被拒绝，重复归还不会复制可用令牌。
- 每池最多`PREFETCH+2=5`份缓冲。小于1MiB的帧保持原分配；五份payload超过预算时也保持原分配：每Reader raw128MiB，每Writer输出64MiB。4K样例适用；8K按这些预算不缓存，不声称已测8K整段性能。
- 私有池管理明确所有权及在途租约。上限是缓冲payload，不是总RSS。普通write调用未使用acquire时不受租约限制。
- 输出每帧仍完整写入Y/U/V；池不缓存旧画面、不减少解码/帧核验/音轨检查，也不改帧映射、遮罩、调色或编码设置。

## 验证与限制

smoke32覆盖池上限/回退、取消等待、重复归还、write确认前不能复用、重复提交拒绝、写失败归还、默认raw与返回BGR的所有权及关闭读线程。smoke33强制小样例启用池，对比完全禁用池的整片和两个span：None/重复映射、fade、调色、小数仿射和原音轨；另用真实bgr24源核对RGB不回收。

完整本地NumPy/native六套回归与三平台CI必须通过后合并；最终状态以对应PR为准。历史发行ZIP和安装技能不替换。没有测试冷OS缓存、10bit/HDR、长片多人压力、用户视觉验收；频率和后台负载未控制。
