- `qc_tools.py precheck`／`seam`／`offset`：一次命令内每个输入只完整解码一次（PR #19 计划 P1 第一步）。此前 precheck 对源片解码 2 次、返回片 4 次（自身、`merge_plan`、再经 `seam` 重复一遍），offset 带 `--motion-region` 时两个文件各 2 次，seam 返回片 2 次。现在同一命令内再次探测、且文件身份（设备、inode、大小、mtime）未变时复用首次结果；身份变化即重新解码，探测期间文件变化即报错；严格探测从不复用；命令结束即丢弃，不跨命令、不进入 merge 或成片校验。6 个 QC 命令在合成片上的输出与改动前逐字节相同。抽样不变。
- `qc_tools.py precheck`：几何抽样与接缝分数改为一遍顺序读取（PR #19 计划 P1 第 4 步）。此前 precheck 自己读一遍，再调用整个 `seam` 命令重新载入配置、重做 `merge_plan` 逐帧检查并再读一遍；Reader 4 个 → 2 个。两类样本仍各自保持原帧集合（precheck 抽样帧与 seam 每 step 帧取并集读取、分别计算），precheck 内的接缝摘要与单独 `seam` 同 step 结果相同。4 种配置（含未映射/重复帧、fade、调色、fit_exclude、关键帧仿射与遮罩、多频段、短 target）× precheck 3 种 samples、seam 2 种 step 共 20 组输出与改动前逐字节相同。1080p 240 帧 precheck 中位数：v2.9 8.34 s → 共享探测 6.42 s → 单遍读取 5.30 s（交替各 3 次，单机合成片观测）。
- `qc_tools.py offset --motion-region`：两个区域从同一遍读取中取出（PR #19 计划 P5 offset 第一项），此前每个文件读两遍。合成片 3 组参数与 1080p 自比对输出逐字节相同；1080p 240 帧、整宽区域：33.6 s → 20.0 s（交替各 3 次中位数）。
- `merge` 同一帧有多个相距较远的补丁时，按色度安全分组分别转换（PR #19 计划 P4），不再把所有裁切框的外接大框整体做 YUV→BGR→YUV。可能共享 2×2 色度块的补丁（偶数对齐框相交）归同组，组框再相交则继续合并；组内顺序、裁切、缩放、融合与写回规则不变。送入编码器的像素与单一外接框逐字节相同：709 limited／601 full／RGB 输入 × 远离奇数坐标缩放、相邻共享色度块、连锁合并、仿射＋保护区＋多频段＋调色、单补丁 × numpy／native 共 30 组成片字节相同。4K 48 帧、三个 400×400 补丁分布在三角：转换面积约 −93%，端到端中位数 numpy 17.08 s → 11.58 s、native 12.14 s → 8.76 s（`FLOW_SEGMENTS=1`，交替各 3 次）。
- `merge`：当前导出区间（`--frames` 或 `FLOW_SEGMENTS` 的一段）完全用不到的返回片不再启动解码器（PR #19 计划 P2 第 5 步）。此前每个补丁都创建 Reader，其 FFmpeg 进程立即开始解码并预读 3 帧。两补丁合成片上完整、分 2 段与 `--frames 0:12` 导出的成片与改动前逐字节相同。
- `merge --frames START:END`（检查用导出）只对导出区间内的帧做逐帧裁切比例、遮罩与仿射空洞核对（整合 PR #17，PR #19 计划 P2）。`--frames` 区间合法性检查提前到计划之前。与区间不相交的补丁仍核对第一帧，格式错误照样拒绝；报告 `scope.per_frame_checks` 注明范围。完整导出与 `--dry-run`（含 `--dry-run --frames`）仍核对全部补丁帧。720p、480 帧逐帧关键帧仿射与遮罩的多频段补丁，导出 2 帧检查片：3.84 s → 1.85 s（交替各 3 次中位数，无缓存），检查片与改动前逐字节相同。

## v2.9

- 新增 `flow_patch.py regrid --source X.mkv --output X.mp4`（issue #13）：普通 `-c copy` 把 MKV 转为 MP4 时保留毫秒取整的时间戳与包时长（如 23.976 fps 得到平均帧率 240000/10009），恒定帧率检查拒收。`regrid` 码流复制并把每个视频包时间戳移到最近的 n/fps（实测不到 1 ms），之后严格探测、逐帧解码哈希与音轨载荷均须与源片相同，报告记录最大移动量与命令；帧离网格超过四分之一帧即拒绝，不做静默重定时。FFmpeg 新旧版本的 `setts` 语义不同，脚本依次尝试两种写法、只保留通过校验的一种（6.1、7.0、9.x 已测）。CFR 检查不放宽。规整后的文件可用 `--copy-unpatched`。
- `tools/release.py` 在所有系统都写 LF（issue #12）：此前 Windows 重建时 `TOOL_POLICY.json`、`SHA256SUMS.json` 与 `.sha256` 变为 CRLF，ZIP 哈希不同且工作区出现改动。
- `--copy-unpatched` 复制 0 帧（每个 GOP 都含补丁帧）时给出 NOTICE，说明未省时间（issue #11 D）。
- 修正 v2.8 合并解码后的两处校验漏检（issue #11 流程精简审计）：
  - #14：成片严格解码只解视频，音频包损坏但载荷哈希相同的成片仍会通过。严格解码现同时解码全部音轨；FFmpeg 6.1 在解码线程出错时 `-xerror` 仍退出 0，因此严格模式下 FFmpeg 输出任何错误信息即判失败。
  - #15：`--copy-unpatched` 在复制帧比对失败而回退整片渲染后，成片校验沿用了拼接文件的探测结果，回退渲染的成片未再严格解码。现在只有全部检查通过的拼接文件才被复用，回退时清除该路径的缓存。
- 测试：smoke 24（test_22：普通转封装被拒、regrid 后帧与音轨不变并可走 GOP 复制；test_23：音频包损坏的源片被拒且不发布；test_24：回退后的成片重新严格校验）。

## v2.8

- 每个文件只完整解码一次：一次 FFmpeg 解码同时给出逐帧时间戳、帧数与 murmur3 逐帧哈希。探测用它检查恒定帧率；成片校验用严格模式（`-xerror`），取代原先 ffprobe 探测解码加一次 `-xerror` 全解码；`--copy-unpatched` 的源片哈希直接取自探测时的解码，拼接后的严格解码兼作成片校验。检查项不变，输出不变。
- 去掉繁琐流程：
  - 完整 `merge` 自动生成预填的 `<输出名>.visual-review.json`（文件名、哈希、fps、帧数、技术校验、声明的帧映射、解码与音轨两项），其余人工检查保持 not_run；报告新增 `tools`（实际使用的组件、版本、白名单类别），交付时不再手抄工具清单。
  - `qc_tools.py precheck`：一次给出返回片规格、映射、整体仿射、对齐后残差、颜色偏移、画布空洞、接缝分数和 fits／hard／regenerate 初步结论，眨眼、表情、分区残差仍人工。
  - 必读规则：白名单说明只在首次使用、版本变化或需要清单外工具时读；验收文档每个任务读一次。AGENT_ENTRY.md 精简为几条硬规则；SKILL.md 原则 11、12 合并。
  - 标准流程改为 `doctor` → `merge --frames … --preview` → 完整导出；`--dry-run` 与检查用导出共用探测缓存，不再需要单独 dry-run 或手工裁短片。
  - 维护：`tools/release.py X.Y` 一次完成版本号、包内哈希、可复现 ZIP 与自检。
- `--copy-unpatched` Windows 回退修正（issue #10）：拼接后的检查失败要回退整片渲染时，此前仍有后台 FFmpeg 读取拼接文件，Windows 删除它时报 WinError 32，回退中断。现在拼接后的检查在同一线程顺序进行，回退前等待所有后台校验结束。容器时间基装不下精确帧时间时（如 Matroska 毫秒在 23.976／24／60 fps），开始前就说明原因并整片渲染，不再白做切块与拼接。新增 smoke test_20（提前回退与拼接后回退两条路径，检查不留临时目录）、test_21（预填验收记录与工具清单）、qc_tools precheck 测试。
- 文档补充使用者 Windows 实测：QSV 在 1080p／4K 可用但该样本未更快、8K 被驱动拒绝；8K 内存占用；VLC 与 Resolve 对参数集切换样片的播放、定位抽查；MSVC 需 Windows SDK。
- 1080p 2 分钟合成片：整片合成 98.4 s → 81.3 s，`--copy-unpatched` 35.6 s → 18.6 s；4K 120 帧短片约持平（校验占比小）。

## v2.7

- `merge --copy-unpatched`：按源片关键帧切块，未修补的 GOP 原样复制码流，只渲染、编码含补丁帧的 GOP（B 帧重排延迟与源片一致），拼接后整片探测，并逐帧比对复制部分与源片的 murmur3 解码哈希；不满足条件或任一检查失败即自动整片渲染并给出 NOTICE。适用于 8 位 4:2:0 H.264、时间戳规整的源片。1080p 2 分钟合成片、补丁 130 帧：98.4 s → 35.6 s，补丁外 2750 帧与源片逐比特相同。交付前须在实际播放器／剪辑软件中确认码流中途切换参数集的兼容性。见[参数与命令](references/parameters.md)。
- Windows 实测反馈（issue #8）修正：
  - `remote_run.py run`：`--选项=值` 的值同样检查绝对路径、盘符、UNC 与 `..`；工作机再把含路径分隔符的参数解析为实际路径，不在任务目录内即拒绝。

  - `remote_run.py` 的 `python` 可写不含空格的完整路径。
  - security_test 拆分符号链接与防覆盖用例；Windows 普通账户无权创建符号链接（WinError 1314）时只跳过前者。
  - native-kernels.md 补充 Windows GNU 工具链在中文路径下改用 `rust-lld` 的已验证配置；validation.md 的 v1.2 平台说明归入历史。

## v2.6

经包所有者批准新增三项可选组件，均默认不改变既有行为，范围记录在 `TOOL_POLICY.json` 的 `optional_components_owner_approved`。

- 可选编译内核 `native/`（Rust，仅标准库，经 `ctypes` 调用）：色彩转换、补丁外色度均值、融合与缩放贴回。首次使用前与 NumPy 逐位比对，不一致即停止；`FLOW_KERNELS=auto|native|numpy`。合成 4K 测试 Python CPU 约 28 s → 18 s，总耗时约 18.4 s → 13.7 s（快速编码），输出逐字节相同。见[可选编译内核](references/native-kernels.md)。
- 可选硬件编码 `FLOW_VIDEO_ENCODER=h264_nvenc|h264_qsv|h264_amf`：检查用导出可直接使用；交付与 Flow 上传须 `FLOW_HW_DELIVERABLE=1`（已在该机比较画质）。测试环境无显卡，未实测。
- 远程执行脚本 `scripts/remote_run.py`：`check`／`push`／`run`／`pull`，只用 ssh 连接本地档案中的单个工作机，传输两端比对 SHA-256，不覆盖、不删除。
- `doctor` 显示编译内核状态、编码器与构建中可用的硬件编码器。
- 测试：smoke 17、security 15、remote_run 2；CI 在三个平台分别以 NumPy 与 Rust 内核运行全部测试。

## v2.5

处理提速（完整导出与 v2.4 逐字节相同）、检查用导出、可选分段合成、三平台 CI 及若干正确性修正。不新增工具、依赖、编码器或服务授权。

- 提速：`probe` 一遍解码并同时探测原片与返回片；成片校验各项并行；无关键帧遮罩缓存，静态遮罩／仿射只校验首帧；融合与缩放贴回的逐元素运算按行多线程；恒等调色跳过；`fit_patch.py` 只转换裁切区。读取器提前结束时直接结束解码进程，不再白等 5 秒终止超时；读取器在帧时间戳规整的文件上直接寻址到起点。合成 4K 测试（4 核 Linux）49.5 s → 25.4 s（同尺寸）、38.6 s → 25.2 s（缩放）、50.8 s → 27.7 s（返回片尾部有未用帧），输出哈希与 v2.4 相同。
- 检查用导出：`merge --frames START:END` 只导出指定原片帧（配置帧号不改），`--preview` 用 ultrafast 编码；报告标为不可交付；检查运行缓存未变输入的探测结果。1080p 2 分钟片检查片尾 30 帧由整片合成 125.9 s 降至 3.1–10.2 s。
- 可选分段多进程合成 `FLOW_SEGMENTS`（默认 1 不分段；码流与单进程不同；4 核机器无收益，多核工作机须实测）。
- 交付编码可调：`FLOW_CRF`（默认 17）、`FLOW_X264_PRESET`（默认 fast），实际值记入报告命令。
- `fit_patch.py --motion euclidean|affine`：可选旋转／缩放配准，线性部分变化受 `--max-linear-change`（默认 0.08）约束；默认仍为平移。
- `qc_tools.py seam`：按 [返回片贴合度预检](references/return-fit-assessment.md) 第 5 条，用与合成相同的补丁、遮罩计算过渡带加权高低频差，供候选比较。
- 淡变可分别设首尾：`fade_in_frames`／`fade_out_frames`（`fade_frames` 仍同时设两端）。
- 报告与终端 `NOTICE`：源片为 4:2:2／4:4:4 时说明输出为 4:2:0；多条音轨只保留第一条；字幕、数据、附件流不进入输出。
- 修正：FFmpeg 6.1 等旧版把全范围（yuvj）源片解码成有限范围、Reader 却按全范围解读，导致对比度被压缩；现显式声明范围。毫秒时间基（如 MKV）的恒定帧率源片不再被误判为变帧率。脚本自行以 UTF-8 输出，Windows 不再需要 `PYTHONUTF8=1`。
