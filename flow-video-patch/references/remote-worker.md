# 局域网工作机执行

用户可以指定一台自己的局域网机器承担处理计算。智能体仍在主机上读技能、写参数、做视觉验收，只把白名单脚本的运行放到工作机。

## 启用条件

- 仅当主机存在本地档案 `~/.claude/flow-patch-local/remote-worker.md` 时启用。档案写明 SSH 别名、工作机任务目录、已装版本及用户授权记录；机器名、账号、地址和路径只写在档案里，不写进本包。
- 授权范围：通过档案中的 SSH 别名用 `ssh`／`scp` 连接这一台工作机，在其任务目录内传输任务素材并运行本包白名单脚本与测试。不连接其他主机，不把素材发往任何第三方服务，不在工作机安装或换用清单外工具。这是用户的本地授权，按[工具白名单与审批](tool-policy.md)第 5 步记录，不改变分发包默认白名单。
- 工作机上的白名单组件同样要核对实际版本与构建；与档案记录不一致时先停下核对，不沿用旧结论。

## 脚本执行（v2.6）

`scripts/remote_run.py` 把下文的执行顺序写成命令，只用 `ssh`（OpenSSH 客户端，BatchMode，不弹密码）。需要用户本地档案 `~/.claude/flow-patch-local/remote-worker.json`（不入包）：

```json
{"ssh_alias": "worker", "task_root": "D:/flow-tasks", "skill_dir": "D:/skills/flow-video-patch", "python": "python"}
```

`ssh_alias` 是 `~/.ssh/config` 中的 Host 别名。`python` 可写工作机 PATH 中的名称，或不含空格的完整路径（如 `C:/Python313/python.exe`）；路径含空格时 cmd.exe 与 sh 的引号规则不同，请把该目录加入工作机 PATH 后写名称。命令：

```bash
python scripts/remote_run.py check
python scripts/remote_run.py push job-01 source.mp4 flow.mp4 merge.json
python scripts/remote_run.py run job-01 flow_patch merge --config merge.json --output patched.mp4
python scripts/remote_run.py pull job-01 patched.mp4 patched.report.json --dest ./job-01
```

- `check`：先核对本机副本与其 `SHA256SUMS.json`，再在工作机逐个计算清单所列文件的 SHA-256 并与本机清单比对；任一缺失、不同或清单含不安全路径即停止，不运行工作机上的任何脚本。全部一致后才运行 doctor。
- `push`／`pull`：文件经 ssh 数据流传输，两端比对 SHA-256；不覆盖已有文件，不一致的取回副本自动删除。
- `run`：只运行本包 `flow_patch`、`fit_patch`、`qc_tools`，工作目录为任务子目录。参数（含 `--选项=值` 中的值）不得为绝对路径、盘符、UNC 或含 `..`；工作机再把含路径分隔符的参数解析为实际路径，确认仍在任务目录内才运行。配置 JSON 中的媒体路径是另一信任边界，按 `flow_patch.py` 自身规则处理；这些检查不是操作系统沙箱。本地的 `FLOW_*` 设置（线程、分段、内核、CRF、编码器）随命令转发，其他环境变量不发送。
- 不提供删除；清理工作机文件仍须用户确认后手动进行。

## 执行顺序

1. 运行前：`ssh <别名>` 跑 `python scripts/flow_patch.py doctor`，与档案中的版本对照；工作机技能副本须与主机副本同版本（比对 `SHA256SUMS.json`）。
2. 传素材：每个任务在工作机任务目录下建独立子目录；用 `scp` 传原片、返回片和参数 JSON，传后两端比对 SHA-256。参数 JSON 中的路径用工作机路径或相对路径。
3. 运行：在工作机执行 `prepare`／`merge`／`qc_tools.py`，报告与输出留在该任务子目录，不覆盖旧文件。
4. 取回：把最终成片、报告和必要的预览帧取回主机任务目录，再比对 SHA-256。视觉验收针对取回的最终文件进行，并在记录里注明处理所在机器。
5. 结束：工作机上的素材按用户要求保留或清理；清理属于删除操作，先确认。

## 性能使用

- 不改代码即可用的：互不依赖的任务（不同人物、不同分段、多个候选的预检与 QC）在工作机上并行运行，并发数以 CPU 线程和内存为限，各自独立目录与输出名。
- 编码线程：环境变量 `FLOW_ENCODE_THREADS` 控制 libx264 线程数，未设置为 4（与旧版输出一致），`0` 为按核数自动，上限 64。工作机档案写明其取值；`doctor` 输出当前值，报告的 `command_argv` 记录实际值。不同线程数的 libx264 码流不逐字节相同，同一任务的候选比较保持同一取值。
- 逐帧处理：色彩转换按行分块多线程，线程数由 `FLOW_PROCESS_THREADS` 控制（未设置或 `0` 为按核数，上限 32；可设 1–64），结果与单线程逐值相同。`merge` 只把补丁所在区域转成 BGR 处理；补丁支持区以外的像素直接沿用解码的 YUV，编码前亮度与原片解码值完全相同，色度为解码 4:4:4 的 2×2 均值。支持区内像素及其接触的色度块与旧版计算相同。
- 融合与贴回：alpha／多频段融合及缩放贴回的逐元素运算按行分块多线程（同一 `FLOW_PROCESS_THREADS`），金字塔本身由 OpenCV 多线程；补丁尺寸与工作尺寸相同时直接写入融合结果（与原算式逐值相同）；恒等调色（增益 1、偏移 0）跳过。不带关键帧的遮罩只算一次，`merge_plan` 对不带关键帧的遮罩与仿射只校验首帧。
- 探测与校验（v2.8）：每个文件只完整解码一次。这一次 FFmpeg 解码同时给出逐帧时间戳（按容器时间基，不取整）、帧数和 128 位 murmur3 逐帧哈希；成片校验用严格模式（`-xerror`，遇到解码错误即失败），取代原先的 ffprobe 探测解码加一次 `-xerror` 全解码。原片与各返回片同时探测，成片校验与两次音轨哈希并行，各项检查都不省略。1080p 2 分钟合成片：整片合成 98.4 s → 81.3 s，`--copy-unpatched` 35.6 s → 18.6 s，输出不变。
- 读取器关闭：读取器提前结束时（返回片尾部有未用帧、分段结束）直接结束其解码进程。此前解码器被堵在管道写入上，要等满 5 秒终止超时；合成 4K 测试中返回片尾部多 10 帧时，单次合成由 50.8 s 降至 27.7 s，输出不变。
- 分段多进程合成（可选）：`FLOW_SEGMENTS=N`（1–32，默认 1 不分段）把 `merge` 按帧区间切成 N 段（每段至少 12 帧），各段在独立进程中处理并编码（只含画面），再用 concat 无重编码拼接、一次复制原音轨，最后整片校验（帧数、恒定帧率、全解码、音轨载荷哈希）。送进编码器的像素与单进程相同，但每段独立编码、段首为关键帧，码流与单进程不逐字节相同；同一任务的候选比较保持同一取值。各段的 `FLOW_PROCESS_THREADS` 未设置时按核数平分；`FLOW_ENCODE_THREADS` 为每段的编码线程，总线程约为两者之积。每段读取器从该段首帧开始按帧号取帧（不按时间戳寻址），段首之前的帧仍要解码，段数越多重复解码越多。4 核机器上实测无收益（1 段 26.9 s、2 段 26.3 s、4 段 30.4 s）；收益只在单进程用不满的多核机器上可能出现，须在工作机上实测后再定取值。
- 只重编码有补丁的片段：`merge --copy-unpatched`（v2.7，见[参数与命令](parameters.md)）。长片配短补丁时收益最大，`FLOW_SEGMENTS` 同时让多个渲染块并行；1080p 2 分钟合成片 98.4 s → 35.6 s。
- 读取器起点：探测确认每帧时间戳都在 `n/fps` 网格上（误差小于 1/4 帧）的文件，读取器用 `-ss` 定位到起点帧与前一帧的正中间，不再从片头解码；否则按解码帧号选取。四种合成样例（23.976 带 B 帧、25p 长 GOP、30p、60p 全 I 帧 MOV）在关键帧前后、片尾等起点与顺序解码逐字节相同。
- 检查用导出：`--frames`／`--preview` 见[参数与命令](parameters.md)。1080p、2 分钟（2880 帧）合成片中检查片尾 30 帧：v2.4 只能整片合成 125.9 s；现在首次 10.2 s，探测缓存命中后 3.1 s。
- 解码与写出：每个读取器在后台线程预读最多 3 帧，编码输入由后台线程写出，与逐帧计算重叠；帧顺序与字节不变。编码器中途退出时等待其结束并报告编码器日志。
- 当前限制：各帧仍按顺序合成，多个补丁同帧时依次融合；4K 时每个读取器预读约多占 75 MB 内存。8K 双补丁检查导出实测约 37 s，进程（含子进程）工作集合计峰值约 5.4 GiB（相加值，含重复计算的共享页），8K 任务应预留足够内存。
- 编译内核（可选）：见[可选编译内核](native-kernels.md)；工作机自行构建一次，`doctor` 显示是否启用。
- 硬件编码（可选，v2.6）：`FLOW_VIDEO_ENCODER=h264_nvenc|h264_qsv|h264_amf`，质量参数仍用 `FLOW_CRF`（NVENC 的 CQ、QSV 的 global_quality、AMF 的 QP）。检查用导出（`--frames`／`--preview`）可直接使用；交付导出与 Flow 上传素材须另设 `FLOW_HW_DELIVERABLE=1`，表示已在该机用同一实片比较过它与 libx264 的画质和码率，否则拒绝运行。报告与 NOTICE 注明实际编码器；`doctor` 列出 FFmpeg 构建中可用的硬件编码器。显卡驱动许可证在该机核对。本包测试环境无显卡。使用者实测（issue #10，Windows 11、Intel Arc Pro B70）：`h264_qsv` 检查用导出在 1080p、4K 成功，但该短样本比 libx264 慢（1080p 4.78 s 对 3.60 s，4K 10.37 s 对 9.40 s），同数值 17 下 SSIM 低于 libx264、文件约小一半；8K 被该驱动的 QSV 拒绝（分辨率不受支持）。硬件编码是否提速、画质是否够用须按自己的机器和素材实测，不能默认更快。
- 使用者 Windows 实测（v2.7，Intel Arc Pro B70 机器，libx264 CRF 17／fast、4 编码线程、4 处理线程、Rust 内核，完整导出）：真实 4K 361 帧 93 s（约 3.9 帧/秒，合计 RSS 峰值约 2.8 GiB）；真实 8K 189 帧 248 s（约 0.76 帧/秒，约 9.5 GiB）；60 秒 4K（1440 帧，补丁只在中间 120 帧）整片重编码 384 s。最后一类正是 `--copy-unpatched` 适用的情况，应优先试它和 `FLOW_ENCODE_THREADS=0`。1080p 合成样本上 GOP 复制配合 `FLOW_SEGMENTS` 2／4 进程渲染为 10.8／9.1 s、合计 RSS 1.6／2.8 GiB；进程数越多内存越高，8K 分段前先估内存。
- 实测才能声称提速：给出同一任务在主机与工作机上的耗时对比，不按硬件参数推算。

## Windows 工作机注意

- v2.5 起不需要 `PYTHONUTF8=1`；v2.4 及更早版本仍须设置，否则中文输出会报 cp1252 `charmap` 错误。
- `security_test` 中 `test_replacement_file_survives_failure_cleanup` 在 Windows 上跳过（v2.4 及更早报 WinError 32）：该测试改名仍打开的文件，Windows 本就禁止，所模拟的竞态在该平台不会发生。其他测试失败按真实问题处理。
- 通过 SSH 跑 cmd 命令时注意引号；Git Bash 的 `sh.exe` 可运行 `tests/ffmpeg_regression.sh`。
- 微软 OpenSSH MSI 若在"重新配置"时报 1603 且日志为 `SetPrivilegesOnSshd`／`0x80070424`，是 sshd 服务注册丢失：用 `New-Service` 注册并执行 `sc.exe privs`（与官方 install-sshd.ps1 相同），或先卸载再全新安装。
