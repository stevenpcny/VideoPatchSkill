# 局域网工作机执行

用户可以指定一台自己的局域网机器承担处理计算。智能体仍在主机上读技能、写参数、做视觉验收，只把白名单脚本的运行放到工作机。

## 启用条件

- 仅当主机存在本地档案 `~/.claude/flow-patch-local/remote-worker.md` 时启用。档案写明 SSH 别名、工作机任务目录、已装版本及用户授权记录；机器名、账号、地址和路径只写在档案里，不写进本包。
- 授权范围：通过档案中的 SSH 别名用 `ssh`／`scp` 连接这一台工作机，在其任务目录内传输任务素材并运行本包白名单脚本与测试。不连接其他主机，不把素材发往任何第三方服务，不在工作机安装或换用清单外工具。这是用户的本地授权，按[工具白名单与审批](tool-policy.md)第 5 步记录，不改变分发包默认白名单。
- 工作机上的白名单组件同样要核对实际版本与构建；与档案记录不一致时先停下核对，不沿用旧结论。

## 执行顺序

1. 运行前：`ssh <别名>` 跑 `python scripts/flow_patch.py doctor`，与档案中的版本对照；工作机技能副本须与主机副本同版本（比对 `SHA256SUMS.json`）。
2. 传素材：每个任务在工作机任务目录下建独立子目录；用 `scp` 传原片、返回片和参数 JSON，传后两端比对 SHA-256。参数 JSON 中的路径用工作机路径或相对路径。
3. 运行：在工作机执行 `prepare`／`merge`／`qc_tools.py`，报告与输出留在该任务子目录，不覆盖旧文件。
4. 取回：把最终成片、报告和必要的预览帧取回主机任务目录，再比对 SHA-256。视觉验收针对取回的最终文件进行，并在记录里注明处理所在机器。
5. 结束：工作机上的素材按用户要求保留或清理；清理属于删除操作，先确认。

## 性能使用

- 不改代码即可用的：互不依赖的任务（不同人物、不同分段、多个候选的预检与 QC）在工作机上并行运行，并发数以 CPU 线程和内存为限，各自独立目录与输出名。
- 编码线程：环境变量 `FLOW_ENCODE_THREADS` 控制 libx264 线程数，未设置为 4（与旧版输出一致），`0` 为按核数自动，上限 64。工作机档案写明其取值；`doctor` 输出当前值，报告的 `command_argv` 记录实际值。不同线程数的 libx264 码流不逐字节相同，同一任务的候选比较保持同一取值。
- 逐帧处理：色彩转换按行分块多线程，线程数由 `FLOW_PROCESS_THREADS` 控制（未设置或 `0` 为按核数，上限 32；可设 1–64），结果与单线程逐值相同。`merge` 只把补丁所在区域转成 BGR 处理；补丁支持区以外的像素直接沿用解码的 YUV，编码前亮度与原片解码值完全相同，色度为解码 4:4:4 的 2×2 均值。支持区内像素及其接触的色度块与旧版计算相同。
- 融合与贴回：alpha／多频段融合及缩放贴回的逐元素运算按行分块多线程（同一 `FLOW_PROCESS_THREADS`），金字塔本身由 OpenCV 多线程；补丁尺寸与工作尺寸相同时直接写入融合结果（与原算式逐值相同）；恒等调色（增益 1、偏移 0）跳过。不带关键帧的遮罩只算一次，`merge_plan` 对不带关键帧的遮罩与仿射只校验首帧。
- 探测与校验：`probe` 只做一遍解码（原先两遍），原片与各返回片同时探测；成片校验中的探测、`-xerror` 全解码与两次音轨哈希并行执行，各项检查都不省略。
- 读取器关闭：读取器提前结束时（返回片尾部有未用帧、分段结束）直接结束其解码进程。此前解码器被堵在管道写入上，要等满 5 秒终止超时；合成 4K 测试中返回片尾部多 10 帧时，单次合成由 50.8 s 降至 27.7 s，输出不变。
- 分段多进程合成（可选）：`FLOW_SEGMENTS=N`（1–32，默认 1 不分段）把 `merge` 按帧区间切成 N 段（每段至少 12 帧），各段在独立进程中处理并编码（只含画面），再用 concat 无重编码拼接、一次复制原音轨，最后整片校验（帧数、恒定帧率、全解码、音轨载荷哈希）。送进编码器的像素与单进程相同，但每段独立编码、段首为关键帧，码流与单进程不逐字节相同；同一任务的候选比较保持同一取值。各段的 `FLOW_PROCESS_THREADS` 未设置时按核数平分；`FLOW_ENCODE_THREADS` 为每段的编码线程，总线程约为两者之积。每段读取器从该段首帧开始按帧号取帧（不按时间戳寻址），段首之前的帧仍要解码，段数越多重复解码越多。4 核机器上实测无收益（1 段 26.9 s、2 段 26.3 s、4 段 30.4 s）；收益只在单进程用不满的多核机器上可能出现，须在工作机上实测后再定取值。
- 读取器起点：探测确认每帧时间戳都在 `n/fps` 网格上（误差小于 1/4 帧）的文件，读取器用 `-ss` 定位到起点帧与前一帧的正中间，不再从片头解码；否则按解码帧号选取。四种合成样例（23.976 带 B 帧、25p 长 GOP、30p、60p 全 I 帧 MOV）在关键帧前后、片尾等起点与顺序解码逐字节相同。
- 检查用导出：`--frames`／`--preview` 见[参数与命令](parameters.md)。1080p、2 分钟（2880 帧）合成片中检查片尾 30 帧：v2.4 只能整片合成 125.9 s；现在首次 10.2 s，探测缓存命中后 3.1 s。
- 解码与写出：每个读取器在后台线程预读最多 3 帧，编码输入由后台线程写出，与逐帧计算重叠；帧顺序与字节不变。编码器中途退出时等待其结束并报告编码器日志。
- 当前限制：各帧仍按顺序合成，多个补丁同帧时依次融合；4K 时每个读取器预读约多占 75 MB 内存。改用 QSV 等硬件编码属于更换编码器，须先实测瓶颈、经用户批准，改后重跑全部自检与色彩回归，再用实片对比画质。
- 实测才能声称提速：给出同一任务在主机与工作机上的耗时对比，不按硬件参数推算。

## 后续可改进方向

按预计收益排序；每项都须实测、复验并经用户批准后再改，不能按本表直接声称已提速。

1. **分段多进程合成**：已作为可选项提供（`FLOW_SEGMENTS`）。待在多核工作机上实测选定段数；段首前重复解码可再用关键帧寻址减少（须保证按帧号精确）。
2. ~~遮罩与参数校验缓存~~：已做（无关键帧时只算一次）。
3. **多频段融合提速**：逐元素运算已按行并行（逐值相同）；仍可只在遮罩外接矩形内建金字塔（结果会变，须评估），多个补丁同帧时并行处理。
4. ~~成片校验并行~~：已做，探测也改为一遍解码。
5. **编译型内核**：色彩转换、色度均值、融合用 C++／Rust 实现，须新增并核查编译工具链与分发方式，并与现有精确换算逐值一致。
6. **硬件编码（QSV 等）**：先只用于不交付的预览和 QC 素材；用于成片前须核查驱动与构建、比较画质与码率、重跑色彩回归。
7. **远程执行脚本化**：把"传素材→比对哈希→运行→取回→再比对"写成随包脚本，减少人工命令与路径错误；只允许连接本地档案指定的主机。
8. **Windows 兼容**：脚本内部统一按 UTF-8 输出，不依赖 `PYTHONUTF8`；文件占用替换测试在 Windows 上改为跳过并注明原因。
9. **预读深度可配置**：高分辨率多补丁时控制内存，低内存机器可减小预读帧数。
10. **实片计时基线**：用真实任务记录各阶段耗时，作为后续优化取舍依据；合成测试数字不代表实片。

## Windows 工作机注意

- 设置 `PYTHONUTF8=1`，否则中文输出会报 cp1252 `charmap` 错误。
- `security_test` 中 `test_replacement_file_survives_failure_cleanup` 在 Windows 报 WinError 32：该测试改名仍打开的文件，Windows 本就禁止，所模拟的竞态在该平台不会发生。其他测试失败按真实问题处理。
- 通过 SSH 跑 cmd 命令时注意引号；Git Bash 的 `sh.exe` 可运行 `tests/ffmpeg_regression.sh`。
- 微软 OpenSSH MSI 若在"重新配置"时报 1603 且日志为 `SetPrivilegesOnSshd`／`0x80070424`，是 sshd 服务注册丢失：用 `New-Service` 注册并执行 `sc.exe privs`（与官方 install-sshd.ps1 相同），或先卸载再全新安装。
